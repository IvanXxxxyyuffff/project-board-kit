# 更新说明（每次改动必写一条）

> 规则：没有更新说明的改动不算完成。
> 目的：让下一个人（或三个月后的你）能在 30 秒内知道「这次改了什么、为什么、影响哪里」。

---

## 1. 写在哪

仓库根 `CHANGELOG.md`，最新在最上面。一条一个版本号，不要在旧条目里改内容（除非修正错误，标注 `(修正)`）。

---

## 2. 统一模板（复制即用）

```markdown
## vX.Y.Z — YYYY-MM-DD

**改了什么**
- （一条一句话，动词开头：修复/新增/移除/重构/调整）

**为什么改**
- （用户看到的现象 / 数据对不上 / 性能 / 维护成本）

**影响面**
- 数据层：（中间 JSON 字段是否变化，旧数据是否兼容）
- 页面/挂件：（可见变化、交互变化）
- 管道/定时：（步骤增删、耗时、失败策略）

**验证**
- L1：<命令> → 期望 <计数> PASS
- L2：<命令> → 期望 <计数> PASS
- 手工：<一句话说明看哪里>

**兼容与回滚**
- 是否需要重跑解析：（是/否）
- 回滚方式：（git revert / 换回旧产物 / 恢复备份文件）
```

---

## 3. 版本号约定

| 位 | 何时加 |
|---|---|
| 主版本 | 数据契约变更（字段增删/语义变化），旧数据必须重生成 |
| 次版本 | 新增能力（新页面区块/新交互/新治具），向后兼容 |
| 修订号 | 修 bug、调样式、改文案，不动契约 |

---

## 4. 反面例子（不要这样写）

- 「修复了一些问题」：无法验证，也无法回滚。
- 「优化了代码」：没说什么行为变了。
- 「按需求调整」：三个月后没人知道哪个需求。

---

## 5. 与发布的关系

1. 先写「改了什么 / 为什么改」（动手前）。
2. 改完补「影响面 / 验证」（提交前）。
3. `CHANGELOG.md` 与代码同一个提交，不分开。

---

## 6. 历史（示例格式，内容按仓库实际填写）

```markdown
## v2.2 — 2026-11-16

**改了什么**
- 新增：检测治具方法文档与自检分层约定
- 修复：同一数字在柱状图/明细/KPI 三处口径不一致
- 移除：仓库中的业务数据与机器路径（改为占位符）

**为什么改**
- 用户按屏幕行数核对，与图表数字对不上
- 交付给他人时不能泄露业务信息

**影响面**
- 数据层：无字段变更
- 页面/挂件：可见数字统一为「明细行数」
- 管道/定时：新增一步覆盖交叉验证

**验证**
- L1：`python research/verify_static.py` → 全绿
- L2：`node research/verify_runtime.mjs` → 全绿
- 手工：任取一天，柱顶数字 == 明细行数

**兼容与回滚**
- 无需重跑解析
- 回滚：`git revert <sha>`
```

## 发布前必跑：一条链走完

顺序固定，不要跳步；任一步失败就先修，再从头跑。

| 步骤 | 目的 | 通过判据 |
|---|---|---|
| 1. 重建套件清单 | `manifest.json` 里的 sha256/字节数与实际文件一致 | 输出 `MANIFEST files=N` 且无报错 |
| 2. 重建导出仓 | 占位化 + 覆盖层 + 清单重建 | 输出 `GATE_BAD_CATS=0` 与 `MANIFEST_REBUILT files=N` |
| 3. 门禁检查 | 敏感词、必备文件、清单、安装顺序、exe 政策、占位符完整性 | `GUARD_RESULT=PASS` 且 `leaked=0` |
| 4. 分离部署演练 | 克隆到 A、装到 B，验证安装器改写不会破坏清单 | `doctor` 输出「脚本与套件清单一致」 |
| 5. 打包与推送 | 生成 zip、提交 main | `git push` 成功且 HEAD 前进 |
| 6. Release | 版本条目 + 资产 | 资产体积与本地 zip 一致 |
| 7. CI | 远端门禁 | workflow 结论 `success` |

为什么必须做第 4 步：安装器会把 `<ROOT>` 占位符改写成本机路径，只有「克隆目录 ≠ 安装目录」才能暴露「谁被误改写」；同目录部署会命中未改写的套件源，永远看不出问题。

典型失败与处置

| 现象 | 原因 | 处置 |
|---|---|---|
| 清单不一致 | 改了套件文件没重建清单 | 回到第 1 步 |
| `leaked>0` | 占位符被写成绝对路径 | 源文件改回 `<ROOT>`，回第 2 步 |
| 分离部署 `doctor` 报被改过 | 安装器把自身/校验脚本的占位符也改了 | 把该文件加入安装器排除名单 |
| 资产过小 | HEAD 是空树 | 先提交再打包 |
| CI 红 | 门禁在远端复检失败 | 看 workflow 日志定位，修完重跑全链 |

### 发布前必跑（两条命令）

```bash
python -X utf8 scripts/guard_meta.py                      # 单文件级门禁：脱敏/清单/一致性
python -X utf8 scripts/prepublish_gate.py --version vX.Y  # 发布级：E01–E10 十项
python -X utf8 scripts/prepublish_gate.py --selftest --version vX.Y   # 治具自身覆盖度
```

顺序不能省：`prepublish_gate` 的 E01 会再调一次 `guard_meta`，所以单独跑 guard 通过并不代表发布级检查通过
（E05 重复章节、E06 版本号、E07 安装链、E08 残留物、E10 文档引用都在 guard 之外）。

## 发布前先跑一次自检（避免逐条返工）

```
本地自检脚本（发布链内部使用，不随仓库分发）
```

它一次跑完 preflight / 导出 / guard / prepublish 与二进制口径回归，把所有失败一次性列全；禁止「改一处、发一次、看一条错误」的循环。

## 仓库侧自检（拿到这个仓库的人）

```
python scripts/selfcheck.py
```

依次检查：清单是否最新、脱敏门禁、发布前检查、二进制口径回归；全部通过输出 `SELFCHECK_RESULT=PASS`。改动代码后先跑它，再谈部署。
